# System Architecture

Kingdom runs planned work through LLM roles. One Go service serves the web app and API. The `kd` command initializes and starts Kingdom, then uses that same API for command line operations. SQLite keeps the durable work record. OpenCode runs model work in a prepared project workspace.

This guide is a map of the current system and the rules that shape it. Use the source map below when you need implementation detail.

## The Main Parts

| Part | What it does |
| --- | --- |
| Web app | Lets operators plan work, follow runs, review results, and manage connections and appearance. |
| `kd` command | Initializes a project, starts Kingdom, and gives operators command line access. |
| Go runtime | Owns workflow state, role authority, approvals, provider execution, and recovery. |
| SQLite and runtime files | SQLite records work state and audit history. Runtime files hold project changes and evidence needed to recover unfinished work. |
| OpenCode | Runs assigned model work on the host or through the configured managed OpenShell backend. |

The web app, command line, and API all work with the same local runtime. They do not each maintain a separate view of a run.

The hosted foundations can bind a project database to one central project. A hosted model selection includes an exact connection ID and revision. The API takes the actor from its trusted authenticator, checks current membership and connection visibility, and validates the exact model and thinking effort from a cached catalog for that connection revision. It stores the complete run selection with all role overrides in the run creation transaction. Planning stores the requesting actor's checked selection with each new operation. Automatic titles copy the exact causal reply snapshot; retries keep their existing snapshot. A missing or foreign snapshot prevents enqueue. These snapshots contain credential references, never secrets, and the worker must check current access again before dispatch. Local API requests do not accept connection references. Hosted execution requires an initialized managed provider, explicit project authentication, and a separate model catalog. A backend name alone cannot enable it. Canonical invocation activation binds the exact retained remote allocation and lease in the same transaction; local activation cannot carry a remote identity.

Hosted project assembly owns its database and private runtime files, while central authentication, credentials, and capability registry remain shared. Each project database incarnation has one immutable native workspace mapping in the central catalog; a lost database or expired uncertain creation cannot reuse that workspace's allocation namespace. Worker routes are fixed, project-scoped HTTPS endpoints authenticated by invocation capabilities, and are installed before project consumers start. Failed cleanup retains the runtime and database for retry. Hosted workspace capabilities omit host filesystem paths. Managed planning starts a new provider session for every invocation and reconstructs its prompt from the canonical conversation. Local planning retains its existing session reuse behavior. Managed Resume is unavailable because the saved provider conversation cannot yet be imported into a new sandbox. Rejection preserves the checkpoint and partial files; an explicit Rerun starts fresh.

The separate `kingdom-central` entrypoint owns HTTPS, login, the project portal, and shared project runtime lifetimes. Server-injected metadata selects central or project UI routing; browser input cannot select a host directory or grant access. The project API authenticator checks current membership and retains the requesting actor on each operation. Bounded startup and active serving have separate lifetimes; completion or cancellation of startup cannot cancel an admitted project runtime. Central shutdown cancels sessions and project consumers before it joins model discovery and closes the capability registry or catalog. A failed close retains shared state for retry. The local `kd` entrypoint remains independent of central credentials, login, and OpenShell installation.

## How Work Moves

Planning is a separate workspace where an operator can shape a task before making a Work Order. It is optional. A Work Order can also be created directly. A planner turn that fails stays in the conversation as a failed reply with its reason; the planner never sees it, and retrying it adds a new reply beside it.

The workflow definition controls which roles run and when decisions happen. In the default workflow, advisor roles help shape the plan, a plan decision comes before implementation, and the work then moves through Build, Review, validation, and a final decision. Some stages record a decision or handoff without starting a model session. An alternate workflow can skip Review and validation. The workflow files define the exact steps.

For provider work, Kingdom prepares the workspace, starts the assigned OpenCode session, and records its activity and result. It checks each result against the role and node rules. Approval settings decide whether Kingdom makes the plan and final decisions automatically or pauses for the operator. Review or validation can send the work back for another pass.

Local execution runs one authenticated OpenCode V2 server on loopback for model discovery and for every planning and execution request. The process entrypoint owns that server and closes it after its consumers drain. Discovery reads location-specific models from the user's OpenCode provider configuration and account store without copying credentials. Discovery does not make a model request or certify provider access. Automatic formatting is disabled in the server; a higher-priority configuration that enables it is reported as incompatible. Each request gets its own immutable profile, whose tools are limited to the role's capabilities, and a session. A Kingdom plugin in the server reports every file or shell tool the request attempts, and Kingdom admits the call before it runs. Shell commands run under the process guardian rather than inside OpenCode. A request is prepared and bound to its invocation before any work is sent, and it settles only from the verified terminal record of its own session. Provider-generated context, retries, and compaction checkpoints are matched to their projected records within that owned request; their scheduling and prose do not grant authority. Read-capable roles can read, glob, and grep, and managed shell commands can select existing directories within their workspace.

Agent Communication Style and Agent Guidance settings are shared workspace state. The built-in `neutral-v1` style is the default. Operators choose a workspace style on the Agents page and can edit role working guidance or select a style override. A theme revision may define a communication preference, but choosing a visual theme in a browser never applies it to agents. Protected role instructions retain identity and minimum duties; editable defaults own working methods, while Kingdom Contracts retain authority, evidence, and workflow/output obligations. User guidance is inserted literally without an Agent Guidance Scope wrapper; runtime permissions, transitions, and response validation remain enforced.

Run creation captures each role's effective settings and the protected prompt catalog revision; planning-session creation captures the Plan Author's effective settings and that catalog revision. Both snapshots are immutable and written in the same transaction as the new resource, so later edits or catalog changes affect new work without changing existing runs or sessions. OpenCode receives the captured role, style, guidance, and Kingdom Contract as the system instruction of the request's own immutable profile.

Each planning operation also captures its model selection when it is queued. Session edits affect new operations. Retries retain the original selection. Automatic titles use the selection of their triggering reply; recovery skips an optional title if it cannot find one unique triggering operation. Migration captures the available session selection for historical operations because earlier session edits cannot be reconstructed.

Dynamic Run Context is streamed at its workflow stage, followed by the snapshot-resolved Final Checks as the last authored section. Each provider attempt atomically captures the exact system prompt and dynamic context under its queued lease; Agent Activity displays both immutable channels, after content verification. Provider-added environment and tool prompts are outside Kingdom visibility. Planning uses one Plan Author identity and the selected mode contract, with mode-specific Final Checks appended after the complete transcript and external context. See the [prompt authoring guide](prompt-authoring.md) for the source map and change rules.

## Authority and Evidence

Kingdom owns the rules for what each role may do, which workflow transitions are legal, and whether a result is complete. Prompts guide the model, but they do not grant authority.

The runtime applies these rules:

* Run and node state changes go through the transition service and must follow the workflow.
* A run provider result belongs to its active attempt and invocation. Kingdom validates the result before it can become canonical.
* A process exit, a piece of text, or a saved file alone does not mean the work succeeded.
* If Kingdom cannot prove that a managed provider process has stopped, it keeps that attempt blocked from replacement. The shared server counts too: its guardian records it before the server runs and leaves durable stop evidence, and a server is proven stopped from that evidence or from the absence of its exact process.
* Shared-provider requests have immutable invocation, lease, server-generation, location, session, profile, and request bindings. Dispatch and tool admission require that exact active owner. Cancellation closes admission; late receipts can resolve existing obligations without authorizing more work.
* A shared server's lifetime is separate from request completion. Settlement requires the request's terminal evidence and closed native-tool and command obligations. A command's own exit status is tool output the agent may react to; success settlement instead rejects forced termination, unproven process trees, and gaps in the command sequence. A read, glob, or grep owes nothing; the unreceipted writes of a server proven stopped and its command claims that never reached a guardian are closed as unknown, because they can no longer happen and the workspace is restored or discarded unless the attempt is a promoted success. Workspace release, replacement, and planning-session deletion cannot use process-guardian closure alone.
* A request's terminal evidence is a verified record of its outcome, response, tool calls, and captured provider events. The settlement that depends on the record stores its digest, only if every projected tool matches a durable admission, so a request has terminal evidence exactly when its outcome is canonical or it was abandoned.
* Kingdom admits a remote provider server only after a verified workspace import. The exact helper must close cleanly with complete retained output, and its archive identity and manifest must match the host-validated input. A clean helper exit alone is not sufficient.
* The hosted foundations retain remote command completion separately from local process guardians. Writer closure revalidates the exact managed process identity, terminal receipt, and output. A missing receipt remains resource debt. An unreceipted native write becomes a closed unknown effect only after the exact provider server stops; it cannot support success. Forced cleanup, requested termination, or incomplete process input/output also prevents success eligibility. A normal provider server shutdown must exit cleanly. The fixed managed launcher closes its owned OpenCode standard-input lease, waits for the child to stop, and joins its control server. Only the matching clean managed receipt can prove graceful closure. These facts do not prove credential revocation or sandbox disposal.
* Hosted worker capabilities retain immutable invocation, allocation, access revision, purpose, and activated request identity. Only token hashes are stored. A single process owns the capability database; recovery rejects tokens from an earlier process. Model requests use a trusted HTTPS proxy with fixed protocol routes, an exact model, an operator-approved endpoint, and credentials resolved outside the workload. The current adapter supports API keys for OpenAI-compatible Responses and Chat Completions; OAuth refresh, local credential ownership, and listener activation remain separate work. Revocation cancels and joins model streams before recording closure; plugin receipts remain available after new admissions are fenced until the provider stops. Each request checks canonical authority, and active streams recheck it every second plus query latency. Explicit revocation notifications provide prompt cancellation and persist fences for known invocation owners. The first issuance can race revocation across separate databases, so orchestration must also cancel the canonical owner. The registry can seal an immutable closure certificate only after an exact permanent owner fence and joined closure of every issued capability, including retained activation identities. An empty issuance set still requires the fence. Certificates retain the registry identity across restart; project settlement must separately retain and validate this proof before it can release remote resource debt. Neither a capability's closure nor a cancelled HTTP stream proves upstream computation has stopped or a sandbox has been disposed.
* The remote command executor atomically retains a canonical shell claim and encrypted launch request before dispatch. It sends Start at most once; uncertain delivery is recovered through Get only. Command results require the exact retained identity, output, and receipt, with no local guardian substitute. A fenced command proven never dispatched has a separate no-start record, not an invented process receipt, and cannot support success. Shell tools use the fixed project-only command scope and project directory. The managed launcher explicitly selects confined file-tool callbacks; these callbacks do not run OpenCode native file effects or accept caller-supplied completion receipts. Default local execution keeps its existing native admission and receipt path. Hosted runtime activation accepts only the initialized managed service; each invocation must still pass its canonical dispatch gate.
* Confined remote file tools retain their exact native grant, fixed helper request, output, and process receipt. A helper result can establish an effect only after clean process closure and complete output; malformed results and forced cleanup retain an unknown effect and cannot support success. Caller-supplied native completion cannot settle a helper grant. Shell and file tools share one durable slot per allocation, released only by verified process closure or a separate never-dispatched proof. No timeout or lost response releases that slot. The fixed helper and project-only kernel scope enforce these boundaries independently of the model and provider conversation.
* Remote resource closure requires verified writer closure and project-retained certificates from the configured capability registry. It remains separate from sandbox disposal. Success additionally requires a sealed workspace export and retained output application proof. Run output restores a verified snapshot through the pinned unpublished execution workspace descriptor, with current attempt and lease checks before and after restoration. Hosted assembly uses the mapped project directory for both the initial execution source and final publication; an omitted or different publication root is rejected. An incomplete restoration remains application debt. Planning output and source-only response output from run advisors must match the immutable imported content, including file modes and hashes, and never restore files into the project. Read-only run output still requires the exact current attempt and lease, and retained workspace identity; an optional run execution target must not make that workspace writable. Sandbox release requires the exact archived execution inventory and typed deletion receipt for every historical allocation. Failed unbound preparation can discard a created runtime after those cleanup proofs without inventing a provider answer. A creation that was never claimed has a separate permanent never-created proof; uncertain creation remains debt and cannot be replaced based on name absence. Provider cleanup separates draining writers from final disposal. An issued preparation drains and disposes before abandonment; a bound request whose start was not published drains before canonical invalidation, then disposes. Lost launch authority drains without forcing disposal before recovery settles the owner. Settled remote runtimes are disposed by the existing bounded maintenance loop. An allocation cursor and high-water mark bound fair scans. Active bound requests are excluded, and pending or failed deletion remains durable debt across restarts. These resource gates do not themselves grant prompt dispatch.
* Kingdom cancellation is a runtime decision independent of the provider’s raw terminal outcome. Settlement preserves both facts and still requires closed admissions and resource obligations.
* Cancellation handoffs remain discoverable while awaiting disposal, including after a stop was dispatched before a runtime restart. Observation may finish a proven-disposed handoff; it never authorizes repeating the external stop.
* Rejected provider snapshots remain unverified diagnostics; they never certify a response or tool authority. A rejected request can settle by abandonment only after its admitted effects are closed.
* A failed completion handoff without a verified provider answer retains its original evidence and settles through abandonment in the same transaction as the failed attempt, after exact ownership and closed-resource checks. Missing evidence never authorizes success.
* An interrupted provider attempt saves a resume checkpoint once its request, tools, and commands are proven closed and before the trusted workspace is restored. The checkpoint pins the conversation boundary and the partial-file snapshot, and the source attempt keeps its trusted base. Resume starts a new attempt with a fresh invocation, lease, profile, and request. It may adopt the conversation only along a recovery edge that pins that exact checkpoint, for every interrupted frontier step together. Partial files seed the workspace but never become trusted, and a workspace changed after the checkpoint is a conflict, not something to overwrite. A checkpoint is consumed once a resumed attempt reaches the provider; a Resume attempt that ends before that hands its checkpoint back.
* Planning messages, planning-session role-configuration snapshots, run configuration snapshots, and run activity are persisted so they can be inspected and recovered after a restart.

SQLite is the durable record for workflow state and audit history. Files under Kingdom's runtime and workspace directories support project work and recovery. On startup, Kingdom publishes bundled workflow definitions and their complete graphs in one transaction before dispatch. A retained bundled version must match the compiled content and graph; startup rejects a conflict. The same atomic publication path handles workflow API requests. Kingdom then reconciles unfinished work before it resumes dispatch.

Canonical request content stays immutable while referenced. Planning sessions own their title, message, draft, and planner-activity content, including its chunks and activity digests; deleting a session removes those owned records. A remaining reference from another resource blocks that deletion, preserving shared content.

## Trust Boundaries

Kingdom runs on one host, with state stored in SQLite. Default local startup listens on loopback. The separate central service uses HTTPS, configured OIDC or GitHub login, and current project membership checks. It shares project runtimes within one team. Kingdom does not schedule work across hosts or manage an enterprise identity directory.

Default local execution runs OpenCode on the host in a prepared workspace. Kingdom supervises its lifecycle and checks actions against configured policies. This mode does not provide an operating system sandbox for shell commands or protect against hostile software already running as the local user. Managed execution uses the pinned Kingdom OpenShell profile and managed execution extension. It requires verified process identity, confined file and command tools, workspace transfer, closure evidence, and typed disposal. Stock OpenShell installation alone does not provide this contract. Local startup does not inspect or contact OpenShell unless explicitly configured to use it.

OpenCode is the supported provider engine. GitHub Issues can be imported as project context; Kingdom does not write changes back to GitHub.

Provider preparations can retain an immutable workspace pin before remote source capture. The pin binds the canonical invocation, resource, and lease to an absolute private host path and the opened directory identity. Source capture requires the current preparation and rejects a replaced or symlink root. Historical cleanup can reopen that exact directory after admission closes, but does not gain publication authority. Remote output restoration separately requires the current run lease, an unpublished direct execution target in `attempt_dirty`, and a descriptor that does not alias the source or published root. Planning output does not write back to its project root.

Canonical remote prompt dispatch requires the current owner and lease, open request and preparation admission, exact runtime discovery and admitted creation, an immutable worker manifest and workspace pin, the verified import of that manifest source, and an admitted provider server tied to the retained launch intent. The imported process and server identities must match the authenticated runtime subject. A terminal server, missing proof, or any local process guardian denies dispatch. Managed runtime assembly uses this gate together with current model and plugin capability authorization. Discovery or a configured backend name cannot grant dispatch authority.

External result publication reads canonical snapshot blobs, never the live project tree. The source requires a successful run, a trusted execution target, and the same trusted and published snapshot owned by that run. Metadata and file reads recheck current project access. Partial results, foreign snapshots, protected files, and corrupt blobs cannot support publication. Publication adapters must stage and verify each complete file before they send it upstream.
